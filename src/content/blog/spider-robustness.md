## 先说结论

我没有做任何"反反爬"。没有代理池、没有打码平台、没有无头浏览器指纹伪装。
最后让脚本稳定跑两个多月的，是三个非常笨的工程习惯。

## 一、去重指纹要归一化

标题在不同站点常常差一个空格、一个全角括号，或者末尾多一个"（第二次）"。
直接拿标题做 key，重复率能到 18%。

```python
import hashlib
import re

def fingerprint(title: str, date: str) -> str:
    # 去掉所有空白和标点，只留字母数字和汉字
    normalized = re.sub(r"[\s\W_]+", "", title)
    return hashlib.sha1(f"{normalized}|{date}".encode()).hexdigest()
```

`\W` 在 Python 的 Unicode 模式下会保留汉字，正好符合需要。
归一化之后重复率降到 0，代价是偶尔会把两条标题完全相同但内容不同的公告误判成一条——
权衡下来这个错误方向是可以接受的。

## 二、每个站点单独提交事务

一开始所有站点写在一个事务里，结果某个站点中途超时，整批回滚，
前面已经成功抓到的也白费了。改成每个站点独立提交之后：

- 单个站点失败只丢那一个站点的当天数据
- 脚本被 kill 掉再跑，已提交的不会重复写入

```python
for site in SITES:
    try:
        with db.transaction():
            for item in site.fetch():
                db.insert_ignore(item)
    except Exception as exc:
        log.warning("%s 失败，继续下一个: %s", site.name, exc)
```

关键是 `insert_ignore`——靠数据库的唯一索引兜底，而不是靠代码里先查后插。

## 三、宁可慢十倍，也要可重入

定时任务最怕的状态是"跑了一半"。所以我的原则是：
**任何时刻杀掉进程，重新跑一遍必须得到同样的结果。**

具体做法就一条：所有写操作都是幂等的（`INSERT ... ON CONFLICT DO NOTHING`），
所有外部请求都有明确的超时，不做"必须按顺序完成"的状态机。

## 为什么不做反反爬

因为这些站点的公告是公开信息，本质上是"把网页上已有的内容整理一遍"，
频率也控制在每分钟个位数请求。在这个量级下，把工程细节做扎实比对抗检测更有价值。

真要碰到需要对抗的场景，我的第一反应会是**找有没有官方接口或者数据订阅**，
而不是先写一套绕过方案。
